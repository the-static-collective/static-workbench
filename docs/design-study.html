Proposal v0.1 / 18 September 2026

The browser is the desk.

The Workbench owns presentation, local job supervision, and its own operational journal. Each project continues to own its native identities, schemas, validation, semantics, and consequential decisions. This design adds no universal truth record.

Interaction model

Left: workspaces and active jobs. Center: the selected artifact and useful actions. Right, when needed: the proposed transfer and its result. Begin with task cards; reveal the repository graph only as an optional inspector.

Use ordinary verbs: Open, Compare, Prepare rehearsal, Send selected material, Resume. Keep contract details one click away. Never make the user understand every repository to accomplish one task.

Local deployment

Proposed architecture: a browser client served by one loopback-only supervisor, with explicit per-project process adapters. Keep Python environments and Node dependencies isolated by repository. Avoid requiring Docker, a cloud account, or a model for the initial workflow.

A browser page alone cannot safely supervise these local programs. The supervisor is a separate implementation deliverable. Existing app UIs can be launched in their own tabs while shared viewers mature.

Proposed adapter boundary

This is a Workbench-owned design contract, not an existing repository API. An adapter translates only the versions and operations it explicitly supports.

AdapterDescriptor {
  adapter_id, adapter_version,
  owner_repository, pinned_commit, dirty_workrtree_status,
  operations: [{ operation_id, input_schema_ref, output_schema_ref,
                 declared_effects, authorization_requirements,
                 supports_cancel, supports_reconcile, retry_policy }]
}

prepare(operation, native_input_refs, requested_output_scope)
  -> compatible | unsupported | missing | refused
  + immutable preview + adapter/version pins + disclosure list

execute(preview_ref, attributable_authorization_ref, invocation_id)
  -> job handle (acceptance is not completion)

inspect(job_handle) -> running | complete | failed | unknown
  + native output_refs + native receipt_refs + verification status

cancel(job_handle) -> requested | unsupported | confirmed
reconcile(invocation_id) -> existing receipt | no verified result | unknown

Keep scheduling state separate from native outcomes such as HOLD, REFUSE, DEGRADED, or LIFT. Store native results verbatim; map only their presentation. A bridge cannot turn a receiver refusal into success.

Transfer record

  "schema": "static-workbench.transfer-proposal/v0.1",
  "status": "proposed",
  "source_refs": [{"owner": "owner-id", "native_id": "opaque-id",
                    "schema_ref": "owner-version", "digest": "owner-qualified"}],
  "destination": {"adapter_id": "explicit-adapter", "operation_id": "supported-op"},
  "version_pins": {"adapter": "exact-version", "owner_commit": "exact-commit"},
  "disclosed_fields": ["explicitly-selected-fields"],
  "derived_input_refs": [],
  "authorization_ref": null,
  "native_receipt_refs": []
}

Opaque native identifiers remain owner-qualified. Derived material receives a new identity and a derivation relation. The supervisor's invocation ID is a correlation key, never a replacement for source or destination identity. Unknown schema versions remain inspectable but cannot execute. Revalidate input identity, version pins, output scope, and permission immediately before dispatch; changed inputs invalidate the preview.

Interruption and return

Write intent to a durable local operational journal before dispatch. Record acceptance, process observation, and native completion separately. After a crash, reconcile with the destination before offering a retry. If the destination cannot reconcile or deduplicate, show “Outcome unknown” and require inspection. Never promise exactly-once execution from a browser request ID. Closing the tab must not silently cancel a render. Cancellation is complete only when the adapter confirms it.

Host boundary

Serve on loopback with strict Host and Origin checks, an unpredictable local session credential, CSRF protection for mutations, and no permissive CORS. Do not put secrets in URLs. Launch registered executables using argument arrays, never browser-supplied shell commands. Resolve file references inside declared roots, reject traversal and symlink escapes, restrict child-process environment, and bound resource use and logs. Display imported text as text; sandbox document/media previews. Treat repository manifests as data, not executable installation instructions. LAN/phone access is a separate authenticated deployment decision.

Storage and portability

Use a Workbench-owned SQLite operational journal and job directories, with native receipts retained intact. This is job bookkeeping, not a replacement TranchNode implementation. A later verified storage adapter can deposit selected records with explicit mappings. Offer an export containing selected artifacts, adapter pins, native receipts, and a manifest of missing dependencies; exclude credentials. Disk exhaustion must refuse dispatch or leave a clear incomplete state.

Smallest useful landing

  1. Read-only desk: select a Toaster export directory, display available artifacts and missing material, preserve owner identities.
  2. One real comparison: verify the current Toaster–Dogram bridge, register one supported adapter, preview precisely what crosses, run it, display its native receipt. If the bridge is unavailable, expose a generic Dogram fixture runner separately; never label it a real render evaluation.
  3. Close and reopen the browser; recover the job. Kill the supervisor after dispatch and demonstrate reconciliation or an explicit unknown outcome without automatic rerun.
  4. Add ALEX intake only after verifying its accepted schema and effectful interface. Add other lanes one useful task at a time.

Acceptance evidence

  • Real fixture input yields the same native calculation result as direct CLI execution.
  • Unsupported versions, missing inputs, invalid receipts, stale previews, unauthorized effects, and escaped paths stop the relevant operation with a useful reason.
  • Duplicate clicks cannot create duplicate local dispatch; crash recovery does not silently repeat an uncertain effect.
  • A project failure cannot relabel other projects as failed or successful.
  • Offline startup works; keyboard navigation, narrow screens, readable error messages, and explicit empty states work.
  • A person can complete one comparison without learning the ecosystem vocabulary.

Evidence and open questions
